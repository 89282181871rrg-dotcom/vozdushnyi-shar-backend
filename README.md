# Воздушный Шар

Бонусная crash-игра с турнирной механикой. Прототип для онлайн-этапа,
дисциплина «программирование продуктовое».

Игрок ставит бонусные баллы, шар поднимается, коэффициент растёт. Успел нажать
«Забрать» до того, как шар лопнет — забрал ставку, умноженную на коэффициент.
Не успел — ставка сгорела.

---

## Запуск

### Через Docker — рекомендуемый способ

```bash
docker compose up --build
```

Поднимет сервис и PostgreSQL. Больше ничего устанавливать не нужно.

### Без Docker

Нужен JDK 17 и Maven.

```bash
mvn spring-boot:run
```

Поднимется на встроенной H2, файл базы ляжет в `./data/`. PostgreSQL при этом
не требуется.

### Куда смотреть после старта

| Адрес | Что это |
|---|---|
| http://localhost:8080/swagger-ui.html | API, здесь проходятся все сценарии |
| http://localhost:8080/api/config/public | действующая конфигурация игры |
| http://localhost:8080/api/config/status | откуда читается конфиг, когда применён |
| http://localhost:8080/actuator/health | состояние сервиса |
| http://localhost:8080/h2-console | база, только без Docker |

**Демонстрационный пользователь `demo`** создаётся при старте с балансом
1000 бонусных баллов. Проверить: `GET /api/users/demo`.
Пополнить в любой момент: `POST /api/users/demo/topup?amount=1000`.

### Проверка игрового ядра без фронтенда

Раундовые данные и состояние хранятся в таблице `rounds`. Сервер сам
генерирует crash-точку до старта и не возвращает её в состоянии `RUNNING`.
Для проверки через curl:

```bash
curl -X POST http://localhost:8080/api/rounds \
  -H "Content-Type: application/json" \
  -d '{"username":"demo","theme":"green","betId":1}'

curl http://localhost:8080/api/rounds/{id}/state
curl -X POST http://localhost:8080/api/rounds/{id}/cashout
curl -X POST http://localhost:8080/api/rounds/{id}/settle
```

`cashout` идемпотентен: повторный вызов возвращает тот же завершённый
результат. Коэффициент и время из тела запроса не принимаются, а недостаток
баланса возвращается как `409 insufficient_balance`. Для указанного в задании
пути без префикса также доступен `/rounds`.

## Стек и почему он такой

| Что | Чем | Почему |
|---|---|---|
| Язык и платформа | Java 17, Spring Boot 3.3 | Требование техзадания к основным механикам backend |
| Сборка | Maven | Один файл описания, ничего лишнего |
| Хранение | PostgreSQL (Docker), H2 (локально) | Все состояния в базе, а не в памяти процесса |
| Доступ к данным | Spring Data JPA | Транзакции и блокировки из коробки |

**Всё используемое ПО — свободное и бесплатное.** Ни одной платной или
проприетарной зависимости. Отчёт по лицензиям всех транзитивных зависимостей:

## Структура проекта

```
config/game-config.yml          ← ВСЕ игровые параметры, правится руками
src/main/resources/
  application.yml               настройки сервиса: порт, база, профили
  default-game-config.yml       запасная копия на случай отсутствия внешнего файла
src/main/java/ru/fsp/balloon/
  core/                         игровое ядро: раунды, RNG, бустеры, выплаты
  platform/
    config/                     загрузка конфигурации, валидация, горячая перезагрузка
    user/                       пользователь, бонусный баланс, журнал транзакций
    history/                    история завершённых раундов
    events/                     журнал игровых событий
    extension/                  точки подключения внешних систем
    openapi/                    описание API для Swagger
    seed/                       создание демо-пользователя при старте
```

Разделение намеренное: расчёты, работа с данными, конфигурация и HTTP-слой
лежат отдельно. Секретов в исходниках нет — настройки идут через переменные
окружения и внешний файл, оба варианта в `.gitignore`.

## Управление параметрами игры — обязательный сценарий 5

Все игровые параметры собраны в **одном файле** `config/game-config.yml`.
Он подробно прокомментирован: у каждого параметра написано, что он делает
и какие значения допустимы.

### Как проверить

1. Начните раунд, запомните начисленные очки.
2. Откройте `config/game-config.yml`, найдите секцию `points`, поменяйте
   `perLevel` с 10 на 100, сохраните файл.
3. Начните новый раунд — очков начисляется в десять раз больше.

Перезапускать сервис не нужно. Править исходный код не нужно. В Docker тоже
работает: папка `config` примонтирована в контейнер.

### Как это устроено

Перед созданием раунда сервис сверяет время изменения файла. Изменился —
перечитывает, проверяет и применяет. Уже идущий раунд доигрывает по той
конфигурации, с которой начался: иначе правка файла в середине полёта
поменяла бы правила на ходу и результат стало бы невозможно воспроизвести.

Применить немедленно, не дожидаясь следующего раунда:

```bash
curl -X POST http://localhost:8080/api/admin/config/reload
```

### Если ошибиться в значении

Конфигурация проверяется **до** применения. Любая ошибка — и новая версия
не применяется: сервис продолжает работать на прошлой рабочей конфигурации
и возвращает список проблем с указанием поля и допустимых значений.

```json
{
  "applied": false,
  "message": "Конфигурация отклонена. Работает прошлая рабочая версия.",
  "errors": [
    "math.alpha: допустимо от 0.1 до 2.0, сейчас 5.0. Больше значение — чаще длинные полёты",
    "themes.green.levelMultipliers[1]: значения должны строго возрастать..."
  ]
}
```

Игра при этом не падает и продолжает принимать ставки.

### Что можно настроить

| Секция | Что задаёт |
|---|---|
| `bets` | четыре варианта ставки и сила бустера у каждого |
| `themes.green` / `themes.red` | количество уровней (9 и 12), границы коэффициентов, вероятность бустера по уровням |
| `math` | распределение точки краха, потолок коэффициента, темп роста, доля заведения |
| `points` | очки за уровень, за cashout, за сработавший бустер |
| `reward` | механика награды за раунд, размер коллекции, шансы выпадения |
| `round` | таймаут бездействия, автозакрытие зависшего раунда |
| `upsell` | окно «Закрепи успех», по умолчанию выключено |
| `demo` | имя и стартовый баланс демонстрационного пользователя |

Административный веб-интерфейс не делали сознательно: по критериям файл
с понятными пояснениями равноценен админке по баллам, а времени он требует
несопоставимо больше.

## Математическая модель

Точка краха вычисляется **на сервере до начала полёта** и клиенту не
отдаётся ни в каком виде. Клиент получает только текущий коэффициент и
рисует анимацию — повлиять на исход он не может, только выбрать момент выхода.

Формула:

```
crash = minCrashMultiplier / (1 - u · (1 - houseEdge)) ^ alpha
```

где `u` — равномерное случайное число на `[0, 1)`. Это стандартное
распределение для crash-игр: короткие полёты частые, длинные редкие,
математическое ожидание конечно. Результат обрезается по `maxMultiplier`.

Параметр `alpha` управляет «хвостом»: больше значение — чаще длинные полёты
и крупные выигрыши. `houseEdge` — доля заведения, ровно на неё смещается
распределение.

### Как проверить модель

Не по исходу одного случайного раунда, а прогоном серии:

```bash
curl "http://localhost:8080/api/config/simulate?rounds=10000&theme=green"
```

Эндпоинт прогоняет заданное число раундов на действующей конфигурации и
показывает средний коэффициент, максимум, долю раундов по достигнутым
уровням и долю раундов, где крах случился до первого уровня — то есть
забрать выигрыш было в принципе невозможно.

Поменяйте `math.alpha` в конфигурации и вызовите ещё раз: видно, как
изменилось распределение. Параметр `seed` делает прогон воспроизводимым —
один и тот же seed всегда даёт одинаковый результат, удобно для отладки
и для демонстрации.

## Проверяемость

| Способ | Где |
|---|---|
| Swagger с описаниями и примерами | `/swagger-ui.html` |
| Машинное описание API | `/v3/api-docs` |
| Журнал игровых событий | `GET /api/events` |
| Журнал движения бонусов | `GET /api/users/demo/transactions` |
| Состояние конфигурации | `GET /api/config/status` |
| Health-check | `/actuator/health` |
| Тесты | `mvn test` |

**Журнал событий** пишет `round_started`, `booster_hit`, `cashout`, `crash`,
`config_reloaded`, `balance_topup` с временными метками. По нему видно, что
точка краха и позиция бустера определены до старта раунда, а не подогнаны
по ходу.

**Журнал транзакций** хранит не только сумму операции, но и баланс после неё.
Любое состояние счёта проверяется по журналу, без пересчёта всей истории.

## Целостность данных

- Все состояния — в базе, ничего не живёт в памяти процесса.
- Списание ставки, начисление выигрыша и запись в журнал идут **одной
  транзакцией**. Не бывает состояния «деньги списаны, а раунд не создан».
- Строка пользователя блокируется на время операции с балансом
  (`PESSIMISTIC_WRITE`) плюс оптимистическая блокировка по версии. Два
  параллельных запроса не смогут прочитать один баланс и оба с него списать.
- Нехватка баланса проверяется **на сервере**, а не скрытием кнопки на
  клиенте. Запрос со ставкой выше баланса вернёт `409 insufficient_balance`.

## Готовность к развитию

Границы для внешних систем вынесены наружу заранее, реализации
подставляются как бины Spring:

**`PaymentProvider`** — работа с бонусными баллами. Сейчас `InMemoryPaymentProvider`:
операции имитационные, внешних вызовов нет, как требует постановка. Чтобы
подключить реальную платёжную систему, достаточно написать вторую реализацию
интерфейса и объявить её бином. Игровое ядро и контроллеры не меняются.

**`RewardProvider`** — выдача наград. Сейчас `CollectionRewardProvider`:
фрагменты коллекции, собрал набор — получил бонусы. Награда встроена в
прогресс, а не висит декоративной иконкой. Интеграция с лотерейной системой
встанет второй реализацией того же интерфейса.

Добавление новой темы или нового варианта ставки — правка `game-config.yml`,
код не трогается. Математическая модель отделена от интерфейса: параметры
живут в конфигурации, расчёт на сервере, клиент только рисует.

## Реализовано

- Внешняя конфигурация игры с горячей перезагрузкой и валидацией
- Откат на прошлую рабочую версию при ошибке в файле
- Демонстрационный пользователь, бонусный баланс, пополнение для проверки
- Журнал движения бонусов с балансом после каждой операции
- История завершённых раундов всех игроков прототипа
- Журнал игровых событий
- Swagger с пояснениями к каждому эндпоинту
- Прогон математической модели для её обоснования
- Точки расширения `PaymentProvider` и `RewardProvider`
- Docker и docker-compose, запуск одной командой
- Тесты валидации конфигурации

## Известные ограничения

- Живой рейтинг, турнирная таблица, окно «Закрепи успех» и отдельный экран
  выбора темы не реализованы — постановка относит их к дополнительным
  возможностям, приоритет отдан обязательным сценариям.
- Административный веб-интерфейс не делали: по критериям конфигурационный
  файл с пояснениями равноценен админке.
- Сохранение незавершённой игры на 30 дней не реализовано — постановка
  прямо называет это необязательным.
- Аутентификации нет: прототип однопользовательский, как допускает условие.
